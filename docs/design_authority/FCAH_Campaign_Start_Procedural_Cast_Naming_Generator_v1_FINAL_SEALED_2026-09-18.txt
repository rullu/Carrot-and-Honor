4. GENERATION TIMING, SEED AND REPRODUCIBILITY
======================================================================

- Generate the complete starting cast for all 43 Realms once, before bootstrap and before play.
- Do not lazily generate rulers when first encountered.
- One campaign seed drives the entire starting cast.
- campaign_seed is an opaque NONEMPTY STRING.
- generator_version is persisted alongside the seed; v1 begins at integer 1.
- Player Realm selection must not influence cast generation. The same generation inputs produce the same 43-Realm cast regardless of the player Realm chosen afterward.
- No player-facing reroll button.
- Any change to generation logic, generation-affecting name data or locked tuning requires a generator_version bump if it would change reproducibility.

Reproducibility contract:
SAME campaign_seed + SAME generator_version + SAME canonical generation authorities/configuration (including days_per_year) => SAME accepted starting cast and SAME deterministic opaque generated IDs.

The generated cast itself is serialized in the save; loading a save does not regenerate it. The seed/version are provenance and recreation/debug information.

Deterministic retries:
- hard/soft validation retries follow a deterministic attempt sequence derived from the same seed;
- retries are bounded; exact attempt cap is implementation detail;
- failed attempts never relax locked rules;
- if no valid cast is produced within the bounded attempts, campaign creation fails loudly.

5. MINIMAL GENERATOR OUTPUT / OWNERSHIP BOUNDARY
======================================================================

High-level generator result:
- campaign_seed
- generator_version
- days_per_year
- realm_setups
- character_setups
- dynasty_setups

The generator does NOT procedurally create:
- Provinces
- Province borders/geometry
- starting ownership
- canonical Realm identity/style/type
- canonical Province culture/religion
- Realm-pair RelationshipState records
- wars
- economy/history/claims filler

Flow:
Campaign-start generator -> CampaignStartValidator -> CampaignBootstrap -> permanent CampaignValidator

CampaignStartValidator owns Day-1-only restrictions. CampaignValidator continues to own permanent structural/lifecycle invariants. This separation is required because later gameplay may legitimately create situations forbidden at campaign start, including personal unions and inter-Realm marriages.

6. NARROW STATE-SCHEMA DELTA — SEALED
======================================================================

CharacterState final v1 campaign-start-facing fields:
- character_id
- given_name              [rename from display_name]
- alive
- sex                      [male | female]
- birth_tick               [authoritative birth/age fact]
- dynasty_id
- realm_id
- personal_culture
- personal_religion
- parent_ids
- partner_ids
- traits
- claims
- history

Rules:
- given_name stores ONLY the personal given name, never title/House/territory/epithet/regnal number.
- parent_ids is unordered and contains at most two known actual parents in v1.
- children are derived from parent_ids; no children_ids field.
- partner links are reciprocal.
- age is derived; no duplicate age field.

DynastyState final v1 campaign-start-facing fields:
- dynasty_id
- lineage_name             [rename from house_name]
- lineage_style            [one of: house, dynasty, clan, family, lineage]
- parent_dynasty_id
- origin_culture
- origin_religion
- claims
- history

Rules:
- lineage is distinct from territory.
- v1 generated default lineage_style by naming family:
  Western = house; Mediterranean = family; Northern = lineage; Central/Imperial = house; Kharven = clan.
- Eastern/Avenic = dynasty for the ruling lineage and house for unrelated supporting/spouse lineages by default; future authored exceptions may override presentation.
- Kharven public style is always clan in v1.
- Newly generated starting lineages use parent_dynasty_id = ""; no procedural cadet branches at start.
- origin_culture / origin_religion are immutable historical origins, not permanent restrictions on descendants.

CampaignState narrow additions:
- campaign_seed: nonempty String
- generator_version: integer
- days_per_year: positive integer campaign timing configuration

The current strict schema is version 1 and still uses display_name / house_name and lacks these additions. Implementation must therefore update the strict schema version (v2 is the intended next schema) and update fixtures/tests. There are no production campaign saves requiring a migration path at this milestone.

7. AGE / TIME CONTRACT — SEALED
======================================================================

- Campaign start is simulation tick 0.
- Characters born before campaign start have negative birth_tick values.
- For a living character, age is derived from current simulation tick and persisted days_per_year.
- birth_tick remains the sole authoritative birth/age fact; do not also store age_years.
- days_per_year is deliberately separate from unfinished month/year presentation. This seal does not choose month names, number of months, seasons or a final calendar.
- Campaign creation must receive a positive days_per_year configuration and persist it; changing it changes generation authorities and therefore reproducibility.
- Starting ruler and living starting spouse minimum age: 18.
- Starting child rulers are excluded in generator v1.
- Hard parent/child floor: every recorded parent is at least 16 years older than the child. This is a generation sanity floor, not a universal marriage/social law.
- Generated living adult ages must be bounded; v1 technical ceiling is 85 unless a future authored exception explicitly overrides it.
- Deceased v1 relatives retain birth_tick, but this milestone does not introduce structured death_tick / age-at-death storage.

Starting ruler age-band weights:
- 18–24: 10%
- 25–39: 32%
- 40–59: 45%
- 60–85: 13%

======================================================================
8. STARTING RULERS, SUCCESSION AND REALM SETUP — SEALED
======================================================================

- Exactly 43 distinct living starting rulers: one per active starting Realm.
- No starting personal unions; the same Character may rule multiple Realms later in gameplay because permanent architecture intentionally allows that.
- Ruler sex tuning: 80% male / 20% female over generation rolls; no culture-specific sex bias.
- Default normal succession_law_id = eldest_legitimate_child.
- Seravelle succession_law_id = elected_office.
- Starting legitimacy = "unresolved" for all Realms. This is a mechanic placeholder, not a political claim that the ruler is illegitimate.
- Normal recognized heir = oldest living legitimate child of the ruler, regardless of sex.
- For campaign-start v1, recognized_heir_id may be empty when no legitimate ruler child exists. Do not manufacture a sibling/cousin just to fill the field.
- Starting recognized_heir_id does not point to siblings/cousins in v1. Extended succession order is future work.
- Seravelle gets no normal hereditary recognized heir.
- Starting ruler children are alive at campaign start. No deceased ruler children are generated in v1, avoiding unresolved grandchild/representation succession branches.
- During later gameplay there is no minimum succession age: an infant/newborn lawful heir may inherit; regency mechanics are future work.

Realm setup adapter:
- official_culture = Realm canonical primary_culture.
- official_religion = full canonical religion record of the Realm's fixed Seat Province, unless a future explicit authored Realm-level exception exists.
- These are copied from canon/setup data; the family generator does not invent them.
- Realm Seat/capital is copied from locked setup.
- original/current political identity, realm_style and polity_type remain canon/bootstrap-owned.
- carrots, faith, claims and history remain neutral/default unless future authored content explicitly supplies them.

======================================================================
9. FAMILY / MARRIAGE CONSTRUCTION — SEALED
======================================================================

Starting marital-status weights:
- unmarried: 35%
- married: 55%
- widowed: 9%
- remarried: 1%

Age-aware application:
- widowhood skews away from very young rulers;
- remarriage is effectively unavailable to very young rulers;
- exact internal conditional weighting may be implemented freely so long as the above world-level direction and hard age rules are preserved.

State representation:
- unmarried => no spouse record; because starting bastards are excluded, unmarried also => 0 legitimate children.
- married => one living spouse.
- widowed => one deceased spouse Character, even if childless; otherwise widowed would be indistinguishable from never married.
- remarried => one deceased former spouse + one living current spouse.
- at most one living spouse at campaign start; no random polygamy v1.
- deceased spouse is a proper CharacterState with permanent ID, alive=false and reciprocal partner reference; never current ruler/heir.

No starting inter-Realm marriages. Ruler, spouse, generated children and generated close relatives start with realm_id equal to that Realm. Deceased spouse/parent retains the last relevant Realm affiliation.

Spouse identity:
- spouse normally weighted toward ruler culture;
- mixed culture/religion is allowed only where the Realm's canonical starting footprint genuinely supports that identity;
- generator must use explicit canonical culture/religion data and must never infer religion from culture name alone.

Children — conditional distribution used only for married/widowed/remarried rulers:
- 0 children: 42%
- 1 child: 26%
- 2 children: 18%
- 3 children: 9%
- 4 children: 4%
- 5 children: 1%

These are weights, not quotas. Because unmarried rulers are forced to 0 children, overall campaign childlessness is intentionally higher than 42%.

Starting illegitimate children/bastards are excluded from v1.

Bloodline inheritance:
- ruler keeps own lineage.
- spouse keeps own birth lineage; marriage does not merge lineages.
- legitimate children belong to the reigning ruler's lineage regardless of ruler sex.
- no patrilineal/matrilineal marriage-mode system in v1.
- every unrelated spouse has a real DynastyState/lineage record.
- ruler siblings share ruler lineage; spouse siblings/parents use spouse lineage logic as appropriate.

Generated parents:
- if ruler parents are generated, one is chosen as the lineage parent and shares the ruler's dynasty_id; the other may have an unrelated lineage.
- lineage-parent choice has no sex bias.
- no extra persistent "lineage parent" field is required; resulting dynasty_id relationships are sufficient.

Personal culture/religion:
- ruler normally starts with Realm official culture/religion unless future authored exception.
- spouse keeps own generated personal culture/religion.
- ruler children start with ruler-parent's culture/religion.
- future upbringing/conversion/assimilation may change personal identity later.

======================================================================
10. FAMILY-TREE SCOPE / OPTIONAL RELATIVES — SEALED
======================================================================

Core generation: ruler + marital state + children needed by that state.

Extended Family Tuning v1:
- ruler sibling(s): 35% chance to generate at least one
- living parent(s): 20%
- aunt/uncle/cousin branch: 5%
- grandparents: not generated by default
- distant relatives: only if later required for a concrete authored/claimant purpose

These rolls do not independently explode into giant trees. Generation stops once a coherent bounded family exists.

Dead relatives are generated only when they represent selected state or are needed for coherence (e.g. widowed status, parent of a living child, half-sibling explanation). Do not generate dead relatives as decorative genealogy.

======================================================================
11. GENERATED IDS / IDENTITY — SEALED
======================================================================

- Character and Dynasty IDs are deterministic, stable, opaque, case-sensitive strings.
- IDs do not encode display name, title, Realm, job or lineage semantics.
- Example style only: character_7f3a91c2; the exact encoding is implementation detail.
- Same generation inputs/version produce the same generated IDs.
- A character changing name/title/Realm does not change ID.
- Given names may repeat freely; even the same given-name + lineage combination may recur across generations. IDs disambiguate identity.
- Unrelated starting lineage identities/names must be unique within a campaign.
- No accidental procedural cross-Realm starting-dynasty webs.

======================================================================
12. NAMING MODEL / WEIGHTS — FINAL V1
======================================================================

FCAH does not use one universal first-name + surname system. Personal given name, lineage, patronymic, territorial style, epithet and office/title are separate concepts.

CharacterState.given_name contains only the given name. DynastyState.lineage_name contains the lineage display name. Titles, territorial style, epithet and regnal numbering are separate presentation/history layers.

For multi-culture regional master pools, affinity weights are:
- Primary = 5
- Shared = 3
- Rare = 1

Anything not explicitly Primary or Rare for a culture is Shared. Cultural affinity and independent base-frequency are conceptually separate. For Generator v1, ordinary non-soft entries use base frequency 1 unless a future authored/tuning table explicitly overrides it; therefore affinity 5/3/1 is the effective ordinary-name weighting.

Soft/rabbit-world overlay — Generator v1:
- 8% chance that a generated given-name selection uses the global soft-name overlay.
- Overlay is unisex; this allows names such as Briar on any sex, consistent with the naming draft's intended use.
- natural soft names use normal overlay weight: Hazel, Hasel, Rowan, Briar, Sorrel, Linden.
- conspicuous soft names use approximately one-third of normal overlay weight: Mallow, Fern, Clover, Thistle, Bramble, Moss.
- overlay-listed strings that also appear in regional pools must not be double-counted as ordinary high-frequency entries; implementation should treat the overlay branch as the controlling soft-name frequency mechanism.
- 8% is v1 tuning, not sacred lore and may be adjusted after generated-cast inspection.

The older ~70% serious / ~20% FCAH-native / ~10% soft balance remains an aesthetic direction, not a second mechanical quota.

======================================================================
21. ABILITIES / PERSONALITY — BOUNDARY
======================================================================

Starting ruler abilities/personality remain mostly randomized with only weak contextual bias when those systems exist. Culture/Realm must never deterministically stereotype a ruler as good/bad or force a specific personality/stat profile.

Exact traits, stats, ranges and gameplay effects remain deferred. Generator v1 must not invent hidden stability/personality scores merely to satisfy campaign-start sanity.

======================================================================
22. CAMPAIGN-START HARD VALIDATION — SEALED
======================================================================

CampaignStartValidator must reject at minimum:
- not exactly 43 active starting Realms / not exactly one distinct living ruler per Realm;
- starting personal union / one ruler assigned to multiple starting Realms;
- missing/invalid fixed Realm Seat or Seat not owned by its Realm;
- invalid canonical Realm culture/religion handoff;
- ruler younger than 18 or older than v1 generated ceiling unless explicit authored exception;
- living starting spouse younger than 18;
- parent younger than child or parent-child gap below 16 years;
- more than two parent_ids;
- invalid/nonreciprocal partner links;
- more than one living spouse at start;
- starting inter-Realm marriage;
- duplicate unrelated starting lineage identity/name;
- procedural cross-Realm starting lineage web;
- culturally invalid name selection under regional pool rules;
- invalid lineage public style where a hard convention exists (especially Kharven clan);
- dead current ruler;
- dead recognized heir;
- recognized heir equal to ruler;
- normal Realm recognized heir that is not the ruler's living legitimate child;
- normal Realm with living legitimate children but recognized heir not the oldest living legitimate child;
- Seravelle using hereditary recognized heir / hereditary succession law;
- normal hereditary Realm not using eldest_legitimate_child in v1;
- any starting bastard/illegitimate-child branch in v1;
- any generated deceased child of the starting ruler in v1;
- malformed opaque IDs / unresolved character or Dynasty references;
- cycle in parent ancestry or Dynasty parentage;
- any violation already rejected by permanent CampaignValidator.

Permanent CampaignValidator must NOT acquire Day-1-only restrictions such as "no personal unions" or "no foreign marriage", because later gameplay may legitimately create them.

======================================================================
23. WORLD-LEVEL SOFT SANITY — GENERATOR V1
======================================================================

Soft bounds are broad retry triggers, NOT targets or exact quotas:
- male starting rulers: 25–40 of 43
- rulers aged 18–24: no more than 10
- rulers aged 60–85: no more than 12
- childless rulers: 18–34 of 43
- rulers with 4–5 children: no more than 8
- remarried rulers: no more than 3

The sanity pass may inspect only facts that actually exist in generator v1. It must not fabricate a hidden political-stability score or other undeveloped mechanic.

Hard validity and soft sanity remain separate:
- hard validity: never break; invalid attempt rejected.
- soft sanity: if the whole generated world is freakishly shaped despite individually valid families, deterministically retry.

======================================================================
24. SERAVELLE — SPECIAL START RULE
======================================================================

R008 Seravelle:
- generate a current living office-holder procedurally;
- office-holder may personally belong to a normal lineage;
- office succession is elected, not hereditary;
- succession_law_id = elected_office;
- recognized_heir_id = "" for the office;
- exact election mechanics and final ceremonial office title remain deferred.

======================================================================
25. IMPLEMENTATION ACCEPTANCE ENVELOPE
======================================================================

Implementation may choose internal algorithms freely inside this envelope. It must:
1. preserve existing Gameplay State Architecture rather than redesign it;
2. make only the narrow state/schema additions/renames recorded here;
3. update strict schema version and all fixtures/tests coherently; birth_tick must use a signed integer schema path because pre-campaign births are negative, never a nonnegative count type;
4. generate before bootstrap;
5. validate with CampaignStartValidator before bootstrap and permanent CampaignValidator afterward;
6. preserve deterministic output and bounded deterministic retries;
7. preserve player-choice independence of generation;
8. use canonical Realm/Province identity rather than reconstructing or guessing it;
9. use explicit culture for naming affinity and explicit religion data for personal/Realm religion;
10. never infer identity from matching strings;
11. preserve the fixed Realm Seats and R028 / Seravelle exceptions;
12. generate no economy, claims, wars or fake historical content merely to populate fields;
13. test hard invariants, soft-sanity retry behavior, seed reproducibility, save/load strictness and name-pool exhaustion handling;
14. leave terrain/world-map work locked.

Before implementation, the coding agent should identify any additional hidden failure modes or missing acceptance checks without changing the locked design. If it discovers a genuine design contradiction, implementation stops and the contradiction is brought back for a human decision.
